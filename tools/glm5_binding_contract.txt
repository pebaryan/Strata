## TRAPS THIS TABLE EXISTS TO PREVENT (all measured this phase, all silent)

  1. conv_q/conv_k/conv_v: the header says [d_conv][d_inner] and the pack records (d_inner, 1, d_conv) with
     d_conv FASTEST.  The binding must do reshape(d_inner, d_conv).T - a TRANSPOSE.  reshape(d_conv, d_inner)
     interleaves four channels' taps: attn_output-0 goes from corr +1.00000 / 0.02% to +0.52073 / 90.56%.
  2. The router bias is `exp_probs_b` in the artifact, NOT `ffn_exp_probs_b` (the field name in the kernel
     header).  Binding the wrong key silently drops the bias, and the bias drives SELECTION ONLY.
  3. The output projection: this artifact HAS output.weight; never fall back to the tied token_embd.
  4. The swiglu clamps come from the artifact's own keys (swiglu_clamp_exp / _shexp), never a nearby constant.
  5. KDA state's FIRST index is the KEY axis: pred and the read sum over i, the update is k[i]*delta[j].  The
     other convention agrees at the first token and diverges from the second (it cost a phase).
  6. attention.head_count_kv is an ARRAY: it is the per-layer MLA(1)/KDA(0) table, not a head count.

## 9.2 STAGE 1 - WHERE IT STANDS, AND THE ONE THING TO READ NEXT

The stage itself is written and compiled (src/core/glm_layer.cpp); the fight has been over how to hand it
pointers, and that has narrowed to one fact worth reading rather than guessing:

  * hc_pre is HOST code.  No CUDA in it at all - std::vector, std::sqrt, std::getenv (glm_hc.cpp:58-96).
  * hc_attn_fn is now dequantized (9ac5c58) and lives in a cudaMalloc buffer: `cudaPointerGetAttributes`
    reports it as device, and a DeviceToHost copy of it WORKS.
  * hc_attn_base / hc_attn_scale / attn_norm come from the weight arena.  For those:
      - cudaMemcpy(DeviceToHost) fails "invalid argument", and
      - cudaPointerGetAttributes does not report them as device, and
      - a plain memcpy from the same pointer SEGFAULTS.
    A pointer that fails all three is not a pointer whose kind should be inferred by trial.

NEXT ACTION, and it is a read rather than an experiment: find how the engine's OWN host code reads arena
weights.  src/core/layer.cpp uses WeightRef::data with sform_of / plane_ptrs, and those helpers are the
engine's stated convention for "this WeightRef's bytes, as host code may touch them".  Whatever they do -
managed memory, a host-mapped arena, or a device->host staging step - is what stage 1 must do too.  Do not
guess between memcpy and DeviceToHost again; three measurements have already ruled out both by trial.

UPDATE - cudaMemcpyDefault also faults, so the question is now narrow:

    hc_attn_fn.weight   -> copied 393216 floats OK   (a cudaMalloc buffer, from the 9ac5c58 dequant)
    hc_attn_base.weight -> SEGFAULT inside cudaMemcpyDefault, before it can return an error

The probe values from the direct-pointer run looked plausible for both:
    hc_attn_fn    0x7f8200200000    hc_attn_base  0x7f8cb600c000
    hc_attn_scale 0x7f8cb600c080    attn_norm     0x7f8cb6004000
and hc_attn_base is a 96-byte F32 row that IS in dense.bin (pack row: ne=24, type=0, bytes=96), so it is not a
shape-only row and not a native one.

So the single question to answer - by READING, not by another memcpy variant - is: what does bind_glm_block
actually store in got.ptr for an F32 tensor, and where does that pointer live?  Candidates, in order of
likelihood:
  1. w->data for a pack-resident F32 row is an offset into a HOST staging copy (weights.cpp uses cudaHostAlloc
     for staging at :202), not the device arena - then the correct read is direct, and the fault came from
     something else entirely.
  2. the binding keeps F32 rows pointing into the arena, and the arena in this driver was freed or never
     mapped for host - then hc_attn_fn succeeding and hc_attn_base faulting would mean the arena pointer and
     the cudaMalloc'd dequant buffer differ in kind, which cudaPointerGetAttributes should have said out loud.

Either way it is a ten-line read of bind_glm_block's F32 branchplus weights.cpp's mapping logic.  Three
segfaults have been spent inferring it; the next move is to look.

Note on the record: 062962f used `git add -A`, so it also committed the stage-1 driver mode in
tools/glm5_bind_check.cpp that segfaults.  The branch still builds (the branch's rule is about the build and
its gates, and no gate runs this driver), but the mode does not pass and should not be read as verified.
Leaving the record straight rather than amending history: that file's stage-1 path is UNVERIFIED.

READ RESULT - the F32 pointer question is answered, and it does NOT explain the fault:

    glm_bind.cpp:106    const float* p = (const float*) w->data;      // F32 branch, handed over as-is
    weights.cpp:413     wr.data = dst_base + r.dst_off;                // dst_base is the caller's arena

So an F32 tensor's pointer is arena + offset, the arena is this driver's cudaMalloc, and these are legitimate
device addresses - hc_attn_base 0x7f8cb600c000, hc_attn_scale 0x7f8cb600c080 (96 bytes, rounded to 128).  No
staging copy, no host mapping, nothing exotic.

Therefore pointer KIND is not the explanation, and neither is the direction: cudaMemcpyDeviceToHost returned
"invalid argument" and cudaMemcpyDefault faulted outright for the same tensor that hc_attn_fn - a plain
cudaMalloc buffer - copied from without complaint.

NEXT DIAGNOSTIC, and it is one run: instrument host_copy to print, BEFORE any copy, the raw pointer, the count,
and cudaPointerGetAttributes().type for that exact tensor, and to print the memcpy's returned cudaError_t
separately from cudaGetLastError().  Three segfaults have been spent on a chain of inference; the next step is
to make the failing call report itself.

INSTRUMENTED RUN - THE ANSWER:

    probe hc_attn_fn.weight    ptr=0x7fdf0c200000  want=393216  attr=ok device   copied fine
    probe hc_attn_base.weight  ptr=0x7fe9c200c000  want=24      attr=ok OTHER    SEGFAULT

"other" is cudaMemoryTypeUnregistered: the F32 arena pointer is not a CUDA-registered address, so no memcpy
variant can touch it - which is exactly why memcpy, cudaMemcpyDeviceToHost and cudaMemcpyDefault each failed
differently.  The pointer is invalid, not mis-typed.  That also retires the earlier hypothesis honestly: the
pointer kind was never the question.

THE SHARP DETAIL - and it indicts a change of mine: the bind print loop read these same F32 tensors SUCCESSFULLY
before; that is how 12/12 against the oracle was measured.  The only thing added to the bind path since is the
hc_*_fn dequant branch from 9ac5c58:

    strata::kernels::dequant_q8_0((const uint8_t*) w->native_data, dev_f, n, stream);
    if (stream) cudaStreamSynchronize((cudaStream_t) stream);

which runs during bind, before stage 1 reads anything.  So the leading hypothesis is that the dequant writes past
its buffer and corrupts the arena - plausibly because `n` was taken as t.ne0*t.ne1 element COUNT while the
kernel may expect a block count, or because writing floats into a buffer sized for quantized bytes overruns.

NEXT ACTION: check dequant_q8_0's `n` convention (elements or blocks) against its existing caller in
glm_bind.cpp:49, which for its case passed the same element count.  If the convention is elements, the overrun
is elsewhere and the next test is to bind WITHOUT the hc branch and confirm the F32 pointers read cleanly again
- that isolates it to one line.

READ RESULT - the dequant call is EXONERATED, so my hypothesis was wrong:

    src/kernels/cuda/quantize_act.cu:267
        void dequant_q8_0(const uint8_t* blocks, float* x, int64_t n, void* stream) {
            const long long nb = n / QK8_0;                  // n is an ELEMENT count
            dequant_q8_0_kernel<<<grid, threads, 0, (cudaStream_t) stream>>>(blocks, x, nb);
        }
    kernel (:129) reads blk = blocks + b*34 and writes x + b*32 .. +32

With n = t.ne0*t.ne1 = 393216: nb = 12288 blocks = 417792 bytes read (exactly the Q8_0 tensor's size) and 393216
floats = 1.57 MB written into a 1.57 MB cudaMalloc.  Source is device-resident (w->native_data).  So the
arguments and the extent are all correct, and the overrun theory is dead.

That leaves the corruption unexplained by the call, and the honest next test is narrow: with STRATA_HC_DEQUANT=1,
disable only the part AFTER the kernel - do not push dev_f into out.owned and do not continue with dev_f in
got.ptr - and see whether the arena still comes back unregistered.  That separates "the kernel write breaks the
arena" from "something about holding this second allocation breaks it" (for instance, NativeDense's own
bookkeeping or the WeightRef for hc_attn_fn being replaced rather than the two coexisting).

Still not a reason to guess a fourth variant at runtime: the state that passed 9.1 is the default, and the
opt-in branch is documented as unverified.

A/B TEST - THE KERNEL IS INNOCENT; HOLDING THE ALLOCATION IS WHAT BREAKS IT

    A: STRATA_HC_DEQUANT=1 STRATA_HC_DEQUANT_KERNEL_ONLY=1   (kernel runs, dev_f freed, nothing stored)
       exit=1, and blk.0.attn_norm.weight reads back the VERIFIED values: 0.0703125 / 0.157226562 / 420.698242
    B: STRATA_HC_DEQUANT=1                                    (kernel runs, dev_f pushed to out.owned)
       exit=139, probe hc_attn_base.weight attr=ok other  (cudaMemoryTypeUnregistered)

So the dequant kernel writes correctly - which the convention read already predicted - and the damage comes from
RETAINING the buffer.  An independent 1.5 MB allocation cannot make the arena unregistered by existing, so the
mechanism must be that something downstream frees a pointer it should not: the glb is out.owned, the
GlmBoundBlock's list of allocations it frees.  The question to answer next is therefore narrow and about
lifetime, not arithmetic:

    does anything else in the binding push an ARENA pointer (repacked, F32, or a WeightRef data pointer) into
    out.owned, so that the destructor frees part of the arena - and does adding one more entry change what gets
    freed where?

That is a read of the branches that populate out.owned plus GlmBoundBlock's destructor, and it is the last step
between here and a working stage 1.

Default path is unchanged and still the one that passes 9.1's check: the branch is opt-in, documented as
unverified.

CORRECTION TO MY OWN A/B READING - A's exit=1 was NOT a clean pass

In A (kernel-only) the branch does `cudaFree(dev_f); continue;` BEFORE storing anything, so hc_attn_fn never

HOW THE KDA GATE GETS FLOAT WEIGHTS - THE OPTIONS, MEASURED AS FAR AS THEY GO

The engine's dequantizers are exactly: dequant_q8_0 and dequant_q8_K (quantize_act.hpp), plus dequant_f32 /
dequant_f16 / dequant_bf16 and dequant_s2 for other paths.  There is NO dequantizer for the 22-byte-block type
that blk.0.attn_q.weight actually uses (native_mmvq_weight_bytes case 6), which is why the widened branch read past
the end before it was gated by native_type == 8.

And the pack does not hand attn_q/k/v over as floats either: a default-configuration run reports 12 rows still
"=quantized" in block 0, attn_q/k/v among them, so native serving is the only source for those three.

Three routes to a KDA gate, in order of what they cost:

  1. WRITE THE MISSING DEQUANTIZER.  A Q5_1-style dequantizer for the 22-byte type, with its own parity gate
     against ggml's own conversion (the same discipline the q8_0 one had).  Extensible, and it is the real
     engineering answer - but it is a new kernel plus a new gate, not a step.
  2. GATE THE KERNEL WITH FIXTURE WEIGHTS.  Have the Python side write the oracle's own wq/wk/wv to a file and let
     the driver load them as floats.  Works today and validates kda_forward end to end.  Its limit is the standing
     rule: a gate that builds its own fixtures validates the kernel and never the wiring, so it must be followed by
     a real binding check once route 1 exists.
  3. GATE ONLY WHAT IS ALREADY FLOAT.  Everything else the KDA call consumes in block 0 IS float in the pack -
     conv_q/k/v, ssm_a, ssm_dt.bias, ssm_f_a/b, ssm_beta, ssm_g_a/b, ssm_norm, attn_output and attn_norm are all
     F32 rows - so the smallest real gate is to run kda_forward with wq/wk/wv supplied from a fixture and every
     other weight taken from the engine's own binding.

Route 3 is the recommended next step: it exercises the engine's binding for eleven of the sixteen KDA inputs, needs
one small driver addition (read three matrices from a file), and keeps the fixture honest about exactly which
inputs it substitutes.

--- static inline void get_scale_min_k4(int j, const uint8_t * q, uint8_t * d, uint8_t * m)
static inline void get_scale_min_k4(int j, const uint8_t * GGML_RESTRICT q, uint8_t * GGML_RESTRICT d, uint8_t * GGML_RESTRICT m) {
    if (j < 4) {
        *d = q[j] & 63; *m = q[j + 4] & 63;
    } else {
        *d = (q[j+4] & 0xF) | ((q[j-4] >> 6) << 4);
        *m = (q[j+4] >>  4) | ((q[j-0] >> 6) << 4);
    }
}

--- void dequantize_row_q5_K(const block_q5_K * restrict x, float * restrict y, int64_t k)
void dequantize_row_q5_K(const block_q5_K * GGML_RESTRICT x, float * GGML_RESTRICT y, int64_t k) {
    assert(k % QK_K == 0);
    const int64_t nb = k / QK_K;

    for (int i = 0; i < nb; i++) {
        const uint8_t * ql = x[i].qs;
        const uint8_t * qh = x[i].qh;

        const float d = GGML_FP16_TO_FP32(x[i].d);
        const float min = GGML_FP16_TO_FP32(x[i].dmin);

        int is = 0;
        uint8_t sc, m;
        uint8_t u1 = 1, u2 = 2;
        for (int j = 0; j < QK_K; j += 64) {
            get_scale_min_k4(is + 0, x[i].scales, &sc, &m);
            const float d1 = d * sc; const float m1 = min * m;
            get_scale_min_k4(is + 1, x[i].scales, &sc, &m);
            const float d2 = d * sc; const float m2 = min * m;
            for (int l = 0; l < 32; ++l) *y++ = d1 * ((ql[l] & 0xF) + (qh[l] & u1 ? 16 : 0)) - m1;
            for (int l = 0; l < 32; ++l) *y++ = d2 * ((ql[l]  >> 4) + (qh[l] & u2 ? 16 : 0)) - m2;
            ql += 32; is += 2;
            u1 <<= 2; u2 <<= 2;
        }
    }
}

--- block_q6_K: uint8_t ql[QK_K/2]; uint8_t qh[QK_K/4]; int8_t scales[QK_K/16]; ggml_half d;  (210 bytes)
void dequantize_row_q6_K(const block_q6_K * GGML_RESTRICT x, float * GGML_RESTRICT y, int64_t k) {
    assert(k % QK_K == 0);
    const int64_t nb = k / QK_K;

    for (int i = 0; i < nb; i++) {
        const float d = GGML_FP16_TO_FP32(x[i].d);

        const uint8_t * GGML_RESTRICT ql = x[i].ql;
        const uint8_t * GGML_RESTRICT qh = x[i].qh;
        const int8_t  * GGML_RESTRICT sc = x[i].scales;

        for (int n = 0; n < QK_K; n += 128) {
            for (int l = 0; l < 32; ++l) {
                int is = l/16;
                const int8_t q1 = (int8_t)((ql[l +  0] & 0xF) | (((qh[l] >> 0) & 3) << 4)) - 32;
                const int8_t q2 = (int8_t)((ql[l + 32] & 0xF) | (((qh[l] >> 2) & 3) << 4)) - 32;
                const int8_t q3 = (int8_t)((ql[l +  0]  >> 4) | (((qh[l] >> 4) & 3) << 4)) - 32;
                const int8_t q4 = (int8_t)((ql[l + 32]  >> 4) | (((qh[l] >> 6) & 3) << 4)) - 32;
                y[l +  0] = d * sc[is + 0] * q1;
                y[l + 32] = d * sc[is + 2] * q2;
                y[l + 64] = d * sc[is + 4] * q3;
                y[l + 96] = d * sc[is + 6] * q4;
            }
            y  += 128;
            ql += 64;
            qh += 32;
            sc += 8;

THE ENGINE'S FFN IS CORRECT.  expert_ffn reproduces the oracle's dense_forward to 1.378e-07 absolute on a vector
whose rms is 0.0114 - that is 1.2e-05 relative, which is float32-against-float64 rounding and nothing else.  The
oracle computes in float64 and the engine in float32, so agreement at that level is the best available; the "3
elements off" is the same thing measured against a 1e-5-relative-to-rms threshold that is simply tighter than
fp32-versus-fp64 divergence.  A tolerance of 1e-4 relative would report zero, and neither number indicates a
defect.  What is verified here: the 12288-wide intermediate (not 2048), the one-sided gate clamp path, the SiLU,
the down projection, and the layout of all three matrices as bound.

THE CLAMP IS STILL UNTESTED, AND THE GATE REFUSED TO PRETEND OTHERWISE.  Max pre-activation 0.5146 against a limit
of 10, so zero of 12288 entries are clamped and a PASS would have been a statement about arithmetic this input never
reaches.  The tool returned exit 2 and the word INCONCLUSIVE instead, which is the first time in this port a gate has
declined to pass, and it is the whole reason the assertion was written into it: the engine's own header warns that
with a limit of 10 the clamp is invisible until something exceeds 10, so the caller who forgets it passes most tests.

That max of 0.51 is itself a finding worth keeping: on a REAL block-0 activation the clamp does nothing at all.
swiglu_clamp_exp and _shexp are both 10.0 for every layer, so the clamp only becomes active where pre-activations
grow past 10 - which is not here, and may not be anywhere in the early blocks.  Which means the clamp is currently
unverifiable from real activations alone.

No candidate reproduces it: hc_pre's layer_in token 0 and hc_attn_pre-0 row 0 both sit at relative distance 1.12

WHY THIS DOES NOT BLOCK ANYTHING: a gate requires the SAME input on both sides, not the TRUE input.  The builder

hc_attn_pre-<block>, a real per-block activation - and it is explicitly NOT the chain's true input, because that is
block N-1's output and needs the chain to run.

THE TEST THAT SETTLES IT: build a block-1 fixture and run kda_gate on it.  If the engine matches the oracle there,
the builder is good enough for its purpose regardless of block 0's provenance.  That is the next action, and it is
cheaper than another round of archaeology on a file whose only job is to be the same on both sides.

########  BLOCK 1's KDA GATE FAILS - AND THE PATTERN LOCALISES IT  ########

THE DIVERGENCE IS BRACKETED.  It cannot be xn (beta and g pass) and it cannot be the hyper-connection or the

WHAT IS ALREADY EXCLUDED, each by a check rather than a belief:
  * the conv weights and their repack - the block-0 self-test reproduced all 16 w_*.bin files at 0.000e+00;
  * the conv geometry being block-dependent - block 1's ssm_conv1d_* are (8192, 1, 4) exactly as block 0's;
  * the input - beta and g pass, and both consume xn;

THE NEXT MEASUREMENT, and it is one small change rather than another investigation: kda_gate compares eight stages
and skips xn, qc, kc and vc - which are exactly the intermediates between the last thing that passes and the first
thing that fails.  The fixture already contains all four (inter_xn.bin, inter_qc.bin, inter_kc.bin, inter_vc.bin).
Adding them to the gate's stage list puts the divergence between two adjacent stages instead of across four, and
the first comparison that fails names the operation: qc failing means xn @ wq.T + conv + silu, qc passing with q
failing means l2_norm.  That is the next action, and it is cheaper than any hypothesis.

THE SKIPPED-STAGE PLAN HITS AN INTERFACE LIMIT, AND NARROWS THE SUSPECTS ANYWAY

kda_gate's table reports g, beta, q, k, v, attn, o - and that list is exactly what the engine's KdaIntermediates
struct exposes.  xn, qc, kc and vc, which the fixture contains, are NOT available from the engine, so adding them to
the comparison is an interface change (extend the struct, have kda_forward fill them), not a table edit.  Recorded so
the next attempt does not start by editing the wrong file.

The pattern narrows it further without that change.  In the oracle's recipe:
    beta = sigmoid(xn @ ssm_beta.T)                    -> PASS
    g    = from xn via ssm_f_*/ssm_g_*/ssm_a           -> PASS
    q    = l2_norm(silu(conv1d(xn @ wq.T, conv_q)))    -> FAIL
    k    = l2_norm(silu(conv1d(xn @ wk.T, conv_k)))    -> FAIL
    v    = silu(conv1d(xn @ wv.T, conv_v))             -> FAIL, and much worse

Two of the three failing stages are l2-normalized and the third is not, which explains why v fails worst: a
magnitude error survives in v and is removed from q and k, while a DIRECTION error shows in all three.  So the
conv/matmul/silu step is wrong for block 1, and it is wrong in a way that block 0 does not exercise.

Everything feeding that step has already been excluded by check: xn (beta and g pass), the weights and their conv
repack (the block-0 self-test reproduced all 16 w_*.bin at 0.000e+00), the conv geometry (block 1's ssm_conv1d_*
are (8192, 1, 4), identical to block 0's), the binding (not on this path - kda_gate uses fixture weights), and the
kernel in general (8/8 at two token counts on block 0).

That leaves a data-dependent difference in the engine's conv/matmul/silu path - which is worth stating plainly
because it is the opposite of the usual failure mode.  CHEAPEST DECISIVE PROBE, and it needs no interface change:
the engine's q and k are printed by kda_gate, and if the engine normalizes correctly then each head's 128 values
must have sum of squares 1.  Compute that from the fixture's engine-side output.  A unit-norm q with a wrong
direction localizes the fault to qc; a NON-unit q localizes it to l2_norm itself, which would be a cleaner bug and a
much shorter investigation.  That is one print, not a new build.

########  BLOCK 1 PINPOINTED: THE FAULT IS THE CONV/SILU STEP, AND IT LOOKS LIKE A SCALE  ########

Adding the four previously-skipped stages to kda_gate's table (they were never missing from the engine - the struct
already had xn, qc, kc and vc; the gate simply never printed them) resolves the bracket to a single operation:

    BLOCK 1                                  BLOCK 0 (regression)
    xn   PASS  1.177e-07                     xn   PASS
    qc   FAIL  8.540e+00    <- first failure qc   PASS
    kc   FAIL  4.408e+00                     kc   PASS

So xn is correct on block 1 and qc - the very next stage, and the first thing computed from xn - is wrong.  The
fault is exactly  xn @ w.T -> conv1d -> SiLU,  with nothing else in the bracket.  Block 0 passing all twelve stages
including the four new ones is what makes this a data-dependent fault rather than a broken kernel.

THE SCALE IS THE SIGNAL.  Everything feeding that step has been excluded by check: xn (xn PASSES), the weights and
their conv repack (the block-0 self-test reproduced all 16 w_*.bin at 0.000e+00), the geometry (both blocks
(8192, 1, 4)), the binding (not on this path), and the kernel in general (12/12 on block 0).

What is NOT excluded, and it is the obvious next thing to look at: the fixture's weights for BLOCK 1.  The self-test
proved the builder's weight path is correct by reproducing block 0's fixture exactly - but it has never verified
block 1's weights, because there is no second known-good fixture to compare against.  If block 1's attn_q or
ssm_conv1d_* dequantize differently, both the engine and the oracle would be reading the same wrong numbers...

...except that kda_gate hands the FIXTURE'S weights to the engine, and the fixture's intermediates come from the
oracle reading those same arrays.  So a wrong weight file would move both sides together and could NOT produce a
disagreement.  Which is worth stating because it eliminates the whole family.

The engine's qc maxes at 0.0636 while rel 8.54 against the oracle's scale implies the oracle's values are about an
order of magnitude larger - a scale relationship rather than a direction error.

NEXT MEASUREMENT, one line and no new build: report() prints only the ENGINE's statistics.  Print the reference's
min/max/sum beside them.  The ratio would then be visible directly instead of inferred from rel, and a clean factor
would name the cause - 1/sqrt(hd), a missing conv normalisation, or a g/beta-shaped scaling are the candidates that
fit an order of magnitude on a step that is a matmul followed by a convolution.

########  BLOCK 1: NOT A BROKEN PATH BUT AN AMPLIFIED ONE - qc SITS IN silu's FLAT REGION  ########

The measurement that reframes it, taken from the fixture and the gate's own output:

    stage   ORACLE (fixture)                  engine                      engine/oracle
    xn      [-0.39369, +0.506206]             identical                   1.0     PASS at 1.177e-07
    qc      [-0.00966, +0.031766]             [-0.239512, +0.063593]      7.5
    kc      [-0.02325, +0.023255]             [-0.049464, +0.082915]      3.6
    vc      [-0.00545, +0.005200]             [-0.263415, +0.176064]      48

    xn @ wq.T recomputed from the fixture:  [-7.95, +2.52]   rms 0.384
    oracle qc, its output after conv+SiLU:  [-0.0097, +0.0318]  rms 0.00149

qc COMPRESSES BY A FACTOR OF 257, and the reason is that its pre-activation is mostly NEGATIVE, where SiLU is
approximately zero.  Block 0's oracle qc reaches +/-0.086; block 1's only reaches +0.03.  Block 1 therefore sits
much deeper into SiLU's flat region, and any absolute difference in the pre-activation is amplified enormously in
relative terms.  Block 1 is not exercising a different code path - it is the same path at an operating point where
the output is near zero and the relative error is therefore large.

WHAT THIS MEANS FOR THE DIAGNOSIS.  The fault is a SMALL absolute difference in the pre-SiLU conv output.  That is a
much more specific statement than "qc is wrong": it says the engine and the oracle differ somewhere in
xn @ wq.T -> conv1d, at a magnitude that block 0 does not expose, and that no amount of staring at qc's relative
error will size.  It also means an absolute-tolerance comparison would have shown this as a small number - the
gate's relative-to-scale tolerance is what surfaced it, which is the opposite of the usual complaint.

AND IT NARROWS THE SUSPECT TO THE CONVOLUTION ITSELF, because everything else on that step is now pinned:
        xn        matches the oracle to 1.177e-07 (compared directly)
        wq        the SAME ARRAY on both sides - kda_gate hands the fixture's weights to kda_forward
        conv_q    the same array too, from the same fixture file
        geometry  both blocks (8192, 1, 4)
So the matmul and the weights agree by construction, and what remains is conv1d_causal - four taps, causal padding,
zero state at t=0 - exercised at a magnitude block 0 never reaches.

NEXT: probe the pre-SiLU conv output directly rather than inferring it.  The engine's qc is silu(conv(...)), so the
conv's own output is recoverable in one line - invert SiLU numerically on the engine's qc, or better, have the
kernel emit it.  Comparing that against the recomputed xn @ wq.T, convolved by hand in numpy from the same
fixture's conv_q, puts the conv's absolute error on the table as a single number.

THE CONVOLUTIONS ARE IDENTICAL - READ BOTH SIDES AND THE CONV IS EXONERATED

    engine  src = t + k - (d_conv - 1);
            if (src >= 0 && src < tokens) acc += conv_w[k*d_inner + ch] * proj[src*d_inner + ch];
            out[t*d_inner + ch] = acc / (1 + exp(-acc));           // = silu(acc)

    oracle  shift = k - (D_CONV - 1)                               // -3, -2, -1, 0
            if shift < 0: out[-shift:] += w[k] * x[:T+shift]
            else:         out[:T-shift] += w[k] * x[shift:]

Same correlation, same causal direction, same zero state, and silu applied identically.  Note both index the kernel
as conv_w[k * d_inner + ch], i.e. the (d_conv, d_inner) layout that repack_conv produces - which is why the fixture
must hold the repacked form and why a double repack would be a real bug.  It is not: the gate passes the fixture's
array straight through and kda_forward indexes it in that layout.

So the suspect moves UPSTREAM of the conv, to the matmul that produces proj.  The engine does it with
matvec(w.attn_q, xt, out, di, ne) per token; the oracle does xn @ wq.T.  Those agree in layout - the fixture's
w_wq is (8192, 4096) row-major and that is what matvec indexes - but this is now the only remaining step between a
verified xn and a divergent qc.

ONE INCIDENTAL OBSERVATION, recorded but NOT claimed as the fault: the assemble loop copies `proj` for every t,
    std::memcpy(raw.data() + (size_t) t * di, proj.data(), (size_t) di * sizeof(float));
which writes the SAME di floats into each token's row.  At tokens == 1 that is exactly right and unobservable, and
both the block-0 and the T=5 gates pass, so it is not the cause here - but if `proj` is meant to be a per-token
projection this line would be wrong for tokens > 1, and both fixtures that pass use either one token or a path that
does not reach it.  Worth one minute's confirmation rather than a rewrite.

NEXT, and it is a one-line diagnostic rather than a new probe: have report() print the INDEX of the largest
difference, not just its magnitude.  A difference spread across all d_inner channels says the matmul; one
concentrated at a boundary or at a single channel says the conv or an indexing slip.  That distinguishes the two
remaining candidates with no kernel change and no new build.

########  THE ANSWER: THE ENGINE IS RIGHT, THE BLOCK-1 FIXTURE IS INTERNALLY INCONSISTENT  ########

Recomputing the oracle's own documented recipe - silu(conv1d_causal(xn @ wq.T, conv_q)) - from the FIXTURE'S OWN
xn, wq and conv_q, and comparing against the fixture's inter_qc.bin:

    block 0:  max|recipe - fixture_qc| rel 7.975e-08      the recipe reproduces the fixture
    block 1:  max|recipe - fixture_qc| rel 8.540e+00      it does not

And 8.540e+00 is the SAME NUMBER the engine was reported as failing by, to four significant digits.  The engine's
qc and the fixture's inter_qc agree with each other and disagree with the arithmetic that the fixture's own inputs
imply.  Therefore:

    THE KDA KERNEL IS CORRECT ON BLOCK 1 TOO.  It has been computing what the fixture asks for.  Every stage of
    this investigation that pointed at the kernel - the conv subgion, the matmul, the parameters - was looking at
    code that reproduces the reference data it is given.

The defect is in the FIXTURE: for block 1, inter_qc.bin is not the output of the recipe applied to that fixture's own
xn, wq and conv_q.  A fixture whose parts do not imply each other cannot validate anything, and kda_gate was
faithfully reporting a disagreement between two things that were never consistent.

WHY BLOCK 0 WORKS AND BLOCK 1 DOES NOT is not yet established, and the difference has to be in the builder's
block-1 path rather than in any kernel.  The candidates, none yet excluded:
  * inter_qc is written from the oracle's returned dict, so a key/value mismatch in that dict would produce exactly
    this - a named file that is some other tensor;
  * the input differs in kind: block 0 gets hc_pre's layer_in, block 1 gets hc_attn_pre-1, and the intervening
    quantities (xn) are consumed differently;
  * the conv repack could be applied to the oracle's dict but not to the file, or vice versa.

THE GENERAL LESSON, and it is the same one this file has recorded twice already in other forms: a gate cannot
validate anything if its parts do not imply each other.  The check that found this was three lines of numpy
recomputing the reference from the reference's own inputs - and it should have been the FIRST thing done, before
reading matvec, before reading conv1d_silu, before two rounds of narrowing.  The right order is: does the fixture
agree with itself, THEN does the engine agree with the fixture.  Asking the second question first cost most of a
session and very nearly produced a "fix" to correct code.

TWO THINGS, AND ONE CHANGES THE PLAN

1. THE ORACLE FILE ALREADY HAS A FIXTURE WRITER.  glm5_kda_reference.py contains a writer that emits the raw
   fixture (weights, input, every intermediate, result) and it has a REGRESSION MODE:

       if BAD_CONV and _a.shape == (D_CONV, D_INNER):
           # REGRESSION MODE: emit the conv weights in the WRONG order while the fixture's expected outputs above
           # were computed with the right one, so the parity gate must FAIL.  Flipping in the loader instead would
           # corrupt the expected values too (wrong against wrong) and the gate would pass - which is exactly how
           # the original defect survived every gate.
           _a = np.ascontiguousarray(_a.T)

   That comment describes this session's failure mode in advance: wrong against wrong passes every gate.  It also
   means the block-0 fixture was produced BY THIS WRITER, not by an inline script as assumed, and therefore that a
   hand-rolled builder is the wrong tool for the job - the writer that already exists encodes conventions the
   builder would have to rediscover, which is exactly the rediscovery that produced a false block-1 failure.

   THE PLAN CHANGES: use glm5_kda_reference's own writer for block 1 instead of extending make_kda_fixture.py.  Its
   BAD_CONV mode additionally lets the gate be shown to FAIL on a known-bad fixture, which is a property this port
   requires and which the builder does not offer.

2. THE NEW SELF-CONSISTENCY ASSERTION FIRED ON BLOCK 0 AT rel 4.572e+01, WHILE THE HAND CHECK GAVE 7.975e-08.  Both
   cannot be right, and the difference is where each reads from: the hand check read inter_xn.bin and inter_qc.bin
   from disk, while the assertion reshapes the oracle's IN-MEMORY inter['xn'], whose layout is not the file's.  So
   the assertion is buggy, not the fixture - which is itself the lesson repeating at one remove: the check has to be
   written against something whose layout is known, and a freshly written file is that thing while an in-memory
   array from another module is not.

   The fix, when this is resumed: run the self-consistency check over the WRITTEN files, after writing them, or
   establish inter['xn']'s actual shape first.  Do not trust a reshape of a foreign array - that is the same
   mistake as assuming a dump's container format, which also cost a round.

########  THE ORACLE'S RAW FIXTURE: EXACT LAYOUT, AND WHY IT CANNOT BE INCONSISTENT  ########

glm5_kda_reference.py --raw-fixture FILE writes ONE binary file:

    struct.pack("<6i", N_EMBD, NH, HD, D_CONV, tokens, layer)          # 24-byte little-endian header
    then 17 float32 arrays:
        attn_norm, wq, wk, wv, conv_q, conv_k, conv_v, ssm_a, dt_bias,
        ssm_f_a, ssm_f_b, ssm_beta, ssm_g_a, ssm_g_b, o_norm, wo, x
    then 11 float32 arrays:
        qc, kc, vc, g, beta, q, k, v, attn, o, result

THE PROPERTY THAT MAKES THIS THE RIGHT FIXTURE SOURCE: the weights it writes are the very arrays the model loader
handed to kda_block, and the intermediates are that same call's return.  Nothing is recomputed, reordered or
re-derived on the way out, so a raw fixture is self-consistent BY CONSTRUCTION - it cannot exhibit the defect block
1's directory has, where inter_qc is not what the fixture's own xn, wq and conv_q imply.  Every hand-rolled
conversion step disappears if the gate consumes this.

STRATA_BAD_CONV_FIXTURE=1 makes the writer emit the conv weights in the wrong order while the expected outputs were
still computed with the right one - the known-bad case, built into the reference rather than reconstructed by hand.
Its comment says why the flip has to live in the writer and not the loader: "wrong against wrong ... and the gate
would pass - which is exactly how the original defect survived every gate."

HOW TO CONSUME IT WITHOUT TOUCHING kda_gate: split the raw file into the 29-file directory layout the gate already
reads.  All array sizes follow from the header and the known shapes - attn_norm 4096, wq/wk/wv 8192x4096,
conv_q/k/v 4x8192, ssm_a and dt_bias 64 and 128 respectively (measure which, do not assume), ssm_f_a/g_a 128,
ssm_f_b/g_b 8192, ssm_beta 64, o_norm 128, wo 4096x8192, x tokensx4096, qc/kc/vc/o tokensx8192, g/q/k/v/attn
tokensx8192, beta tokensx64, result tokensx4096.  A splitter should ASSERT that the sizes it assigns consume the
file exactly - that turns the one remaining unknown (dt_bias's length) into a check rather than a guess, and a
mismatch is a hard error rather than a silently shifted read.

kernel path is correct gets answered by data that cannot be self-inconsistent.  That is the next action.
